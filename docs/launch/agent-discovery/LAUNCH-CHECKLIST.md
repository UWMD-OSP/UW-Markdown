# Agent discovery launch checklist

Prepared only. Nothing here submits, publishes, deploys or changes an account. The local connector is not yet ready to claim availability in every directory. Its three read-only tools accept source text and have no account, filesystem or network access. They check hashes but cannot authenticate signatures without keys. No pro-forma profile support is claimed.

1. Owner authorizes the release, launch wiring and each directory submission separately. Keep the current private package and versions unchanged until then.
2. Recheck package/server metadata and the selected MCP namespace against the [MCP Registry quickstart](https://modelcontextprotocol.io/registry/quickstart). DNS/sign-in verification and publication remain owner steps.
3. Prepare a Claude desktop extension or plugin bundle around the existing stdio server and skill; validate/test a clean installation on supported systems. A remote connector needs a separately authorized HTTPS service. See [Claude local MCP guidance](https://support.claude.com/en/articles/10949351-getting-started-with-local-mcp-servers-on-claude-desktop) and [directory submission overview](https://claude.com/resources/articles/build-plugins-for-claude). Do not purchase a plan or submit anything during preparation.
4. For ChatGPT, first verify eligibility for [desktop-only local MCP submissions](https://developers.openai.com/plugins/deploy/desktop-only). These currently require provider approval. A skills-only plugin is a separate possible route; a remote MCP listing needs an approved stable HTTPS endpoint. Follow the [submission prerequisites](https://developers.openai.com/plugins/deploy/submission), not a claim that stdio works as a web connector. Account verification, allowlisting and directory submission are owner gates.
5. Fill the null privacy/terms/support URLs in listing-metadata.json only with approved, live public policies and support destinations. Do not invent a service, account or contact. The repository README accurately describes local processing; it does not substitute for directory legal requirements.
6. Run MCP tests and the actual local stdio protocol against correct/wrong/unsupported/oversized synthetic inputs. Confirm one structured result plus matching JSON text, refusals with codes, and no stack traces or stdout diagnostics. Test the write-record skill commands, twelve builtin class examples and zero-install validator locally. AGENTS.md remains the contributor source; do not ship maintainer-private instructions.
7. After owner approval, wire the staged validator/gallery/llms files using README.md, publish the packages under the separately approved lockstep launch, and check the real public links. A build is not deployment proof. Keep #543 and launch-held cleanup separate.
8. Save `node scripts/adoption-counts.mjs` output privately before/after launch. It requests anonymous aggregate counts only. npm counts include automation; forks are interest proxies, not proven adoption. The outside-issue count excludes the public organization account but cannot classify every bot or maintainer without personal records. Directory installs stay unknown until a documented public aggregate endpoint exists; do not read authenticated analytics or user lists.

The metadata is a portable drafting aid, not a provider schema submission. Recheck provider requirements on launch day; routes and eligibility can change. Sources checked 2026-10-26. Aggregate sources: [npm counts](https://github.com/npm/registry/blob/main/docs/download-counts.md), [fork badges](https://shields.io/badges/git-hub-forks), [issue-search badges](https://github.com/badges/shields/discussions/5943).
