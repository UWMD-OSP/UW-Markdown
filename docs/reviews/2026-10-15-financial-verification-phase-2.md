# Financial verification Phase 2 — connected workflows and package parity

Date: 2026-10-15. Repository: `UWMD-OSP/UW-Markdown`. Prior intake:
[Issue #343](https://github.com/UWMD-OSP/UW-Markdown/issues/343) and

This review builds on that intake rather than repeating M01–M12.

## Result and scope

Phase 2 established three implementation defects outside the unresolved M04/M09
financial definitions: incorrect verifier quantization, Excel reconstruction that
changes source inputs, and chat cash-flow labels inferred from row position.
They have separate bounded implementation PRs: [#347](https://github.com/UWMD-OSP/UW-Markdown/pull/347), [#348](https://github.com/UWMD-OSP/UW-Markdown/pull/348) and [#349](https://github.com/UWMD-OSP/UW-Markdown/pull/349). The first can falsely
verify a financial statement and propagate it into a dated projection. The second
can export a different NOI/cap rate from the same source. The third changes the
financial period a reader sees, while leaving the number itself unchanged. Its proposed
correction conflicts with an existing starter-output conformance baseline and is
on review hold; the baseline remains unchanged pending an owner decision.

New acquisition and class tests connect supported functions rather than proving
only that a dictionary entry evaluates. Fifteen new workflow tests cover positive
and negative NOI, IO/amortizing debt, balanced acquisition funding, aggregate
equity/Y1 returns, missing equity, zero-debt DSCR refusal, multi-tranche selection,
preferred redemption, irregular cash dates, populated hotel F&B/comp inputs and
data-center utility-cost precedence. Independent deterministic oracles use an
annuity sum, integer/rational decimal boundary arithmetic, calendar differences,
line-item sums and bisection; no AI-produced expected financial numbers are used.

These controls do not prove a complete development forecasting engine or universal
spreadsheet compatibility. Construction draw generation, accrued/capitalized
interest, staged debt funding/refinance and automatic forward exit valuation are
not generated by the inspected paths. Authoring and verifying a dated amount is
not generating that amount correctly from a construction model. No private golden
deals or proprietary source workbooks were retrieved.

## Confirmed quantization defect: P2-01

Sources: `packages/uwmd-verify/src/{capital-stack,lease-up}.ts` at base;
Format §§4.24/4.25, Protocol §VIII.5, RFC0026 Excel/verifier quantum parity and
RFC0023 numeric determinism. Existing comparison precisions remain capital-stack
coverage2dp/other sizing4dp and lease-up currency/occupancy precisions. This is
not a revised metric formula or a new financial tolerance.

The original multiplication-then-`Math.round` shortcut has two defects: negative
ties round toward zero, and binary64 multiplication can move a decimal tie below
the boundary. Independent integer-rational coverage oracles demonstrate:

| Inputs / stated value | Required result | Original observed result | Corrected result |
|---|---|---|---|
| NOI -1,125,000; annual service1,000,000; coverage -1.13 | verified | failed | verified |
| Same facts; coverage -1.12 | failed | verified | failed |
| NOI1,005,000; service1,000,000; coverage1.01 | verified | failed | verified |
| Same facts; coverage1.00 | failed | verified | failed |
| Lease-up rent+concessions+TI/LC sum -1.125; stated -1.13 | verified | failed | verified |
| Same row; stated -1.12 | failed | verified; projection could accept it | failed; projection refuses |
| Lease-up sum1.005; stated1.01 | verified | failed | verified |

The fix calls the existing decimal quantizer, guarding nonfinite calculations so
previous overflow disagreement behavior is preserved rather than throwing from
the quantizer. Seventeen new tests cover both verdict directions, occupied-area
boundaries, overflow, and propagation/refusal. Capital-stack before-run:
4 new cases failed/21 prior tests passed. Lease-up/projection before-run:9 failed/
67 passed; the remaining new controls preserve existing behavior. After correction,
all2,599 verifier tests pass. No conformance expected output was regenerated.

This defect concerns the authority of a verification verdict. The examples bound
the demonstrated numerical differences to the tested decimal/ratio boundaries;
they do not demonstrate a realized lending loss or a universal forecasting defect.
Recommend owner/release-engineering evaluation before the next affected publication.

## Cross-package parity and Excel correction: P2-02

The public Parkview example is an existing regression input, not a newly retrieved
private deal. Synthetic mutations keep valuation purchase price7,200,000 and
change only selected NOI-source facts. Source baseline: EGI630,936; expenses
234,301 including58,000 tax; NOI396,635. Dictionary cap rate quantizes at6dp.

| Mutation | Reference/CLI cap rate | Original worksheet subtotal arithmetic and implied cap rate |
|---|---:|---|
| None | .055088 | NOI396,635 →.055088 |
| Remove only stated NOI | null | Still reconstructs396,635 →.055088 |
| Remove tax detail, retain stated totals | .055088 | Expenses176,301, NOI454,635 →.063144 |
| Set stated NOI1,000,000, retain detail | .138889 | Still reconstructs396,635 →.055088 |
| Remove all detail, retain stated aggregates | .055088 | SUM(blank) produces0 →0 |

The original exporter writes EGI as SUM(income detail), expenses as SUM(expense
detail), and NOI as their difference. Its named ranges therefore can hold
**different inputs** from the evaluator. Prior parity helpers often supplied the
stated subtotals directly, bypassing these cells. The before-fix workbook values
above were deterministically computed from actual emitted numeric cells/formulas;
this is emitted-workbook evidence, not a live Microsoft Excel recalculation.

The bounded exporter correction retains live formulas for consistent complete
detail, preserves stated editable aggregate inputs for totals-only records, and
uses explicit unavailable cells/notes when the source aggregate is absent. Actual
source/detail contradictions refuse through existing `EXCEL-EMIT-PATH`; this is a
starter export capability check, not a document-validation requirement.
Canonical-decimal identities such as .1+.2=.3 select a source-preserving literal
fallback rather than an erroneous binary-noise refusal; that fallback retains the
original unrounded source number and explains the editing limitation. No financial
inputs are rounded, and no arbitrary equality tolerance or balancing adjustment is
introduced. Source arithmetic and dictionary definitions remain unchanged.

Compatibility is deliberate: a nonfooting export formerly emitted different
financial inputs; it now refuses. A totals-only input remains editable as an
aggregate, but adding/editing detail in that workbook does not automatically turn
it into a live SUM. An absent input yields explicit unavailability, not a claim
that `#N/A` numerically equals evaluator null. Mixed-use has a separate statement
builder; this correction does not certify that separate path. Eight regression
cases and existing Excel suites assess the bounded behavior.

Other supported paths tested on the same three source cases (base/missing/conflict):
all24 direct CLI/reference metric outputs agree. Baseline eight outputs are
cap.055088, LTV.7, DSCR1.1091, debt yield.078697, price/unit150,000, loan/unit105,000,
loan/SF121.74, CoC.04189. Missing NOI leaves cap/DSCR/debt yield null. Stated NOI1m
produces cap.138889, DSCR2.7963, debt yield.198413; CoC retains the independently
stated Y1 branch. This is a source selection distinction, not CoC drift.

`verifyStatedMetrics` checks source cap token.0551 at4dp: baseline verified
(computed.0551); missing NOI unverifiable (`missing_or_null_input`); changed NOI
failed (computed.1389). Reporting6dp results versus4dp source comparisons follows
RFC0079 and is not a numerical discrepancy.

## M04/M09 design assessments and draft RFCs

The Phase1 contract and numerical demonstrations stand. The new drafts compare
alternatives, financial consequences, compatibility, required inputs, absence/
ambiguity behavior, conformance and architectural ownership:

- [Draft RFC0086](../rfcs/0086-data-center-purchase-price-authority.md): independent
  lineage, common valuation authority, same-basis equality, or explicit summary-to-
  variant binding. Determine whether the prices describe one transaction interest/
  date/currency and which selected source governs before choosing a field or check.
- [Draft RFC0087](../rfcs/0087-hospitality-revenue-reconciliation.md): independent
  lineage, universal equality, optional comparability assertions, or authority-
  specific bridge. Period, actual/forecast basis, revenue scope, eligible supply/
  sales, occupancy population and input precision must be explicit before comparison.

A new precision example strengthens M09's design caution:1m reported revenue /
6,000 occupied nights gives displayed ADR166.67; reconstructing with those nights
produces1,000,020. The probe computes the20 difference. A blanket one-cent equality
would falsely fail rounded observations, while a broad tolerance might conceal
wrong scope. This draft does not invent that tolerance or treat an observation as
a full-precision authoritative model input.

Both drafts remain `draft` with unresolved owner decisions; they implement no
normative fields, formulas, validation obligations or conformance changes. No
alternative is represented as accepted. Recommendation: decide economic basis
and selection first, then accept an implementation-ready RFC with explicit numeric
procedure, compatibility and missing-input verdicts. Preserve canonical RevPAR
and existing price formulas until that decision. Interim release need not wait
for these design choices absent a stronger promised reconciliation guarantee.

## Verification record and limitations

Environment: Linux x86_64 restricted sandbox, Node24.21.0, npm11.19.0, Python3.12.3.
Dependencies resolve to each tested checkout's local workspaces. Source base is
