### Protocol floors assigned here

RFCs 0071 and 0074 each left their §X `requires_protocol` floor to release
preparation. Protocol 2.22.0 is the first release containing either, so both
floors are `>=2.22.0`. This preparation applies the floor in these places:

- **Spec.** Protocol §X, the RFC 0071 and RFC 0074 paragraphs in §VIII.3 and
  §VII.3, and the `module-manifest` schema's `requires_protocol` description,
  which now names both floors.
- **Fixtures.** The 23 `conformance/modules/registry/` manifests that
  redeclare an id of a module they name in `depends_on`. Scenario 16's C is
  excluded, because it names only B, so it is a conflict and not an override.
- **Tests.** The module-runtime tests, whose stand-in constant is now
  `RFC_0071_FLOOR` / `RFC_0074_FLOOR`.

No first-party or corpus module calls `is_calendar_date` or overrides, so no
shipped manifest changes.

### Stale lifecycle wording corrected

These are not semantic changes. They correct places that still called earlier
releases "pending":
- Protocol §V.12 still said RFC 0070's "version/release selection remains
  pending". RFC 0070 shipped in Protocol 2.21.0.
- Format §4.7 called RFC 0070 "implementation pending release".
- Wiki 04 and 05 called RFC 0066 (Protocol 2.19.0) and RFC 0069 (Protocol
  2.20.0) unreleased.
- The CLI README called `verify-cash-flows` and `inspect-property-cash-flows`
  unreleased. Both have shipped since CLI 2.10.0.

   - complete wiki 11's staged-placeholder bootstrap for each module, never

   An anonymous 404 does not prove name availability or account ownership.

   publisher: org `UWMD-OSP`, repository `UW-Markdown`, workflow
   `release.yml`, allowed action `publish`, environment blank. That is the
   four existing packages, reconfirmed, and the two modules, new. Static
   `release:check` cannot establish account state.
4. **Tag.** Separate owner authorization is required for an annotated
   `v2.18.0` tag on the merged preparation commit, with message
   `UWMD 2.18.0 (Protocol 2.22.0, Format 2.0)`, and its push to origin.
   - The push triggers the unchanged workflow for core 2.18.0, CLI 2.18.0,
     signing 0.2.22, batch 0.8.17 and both modules at 0.1.10.
   - npm publication is sequential, not atomic. After a partial failure,
     record what landed, fix only the prerequisite, and rerun the ordinary
     workflow.
   - This preparation creates or pushes no tag and executes no npm
     publication.
