# UW Markdown — Independent Project Review

**Reviewed:** 2026-04-26
**Repo state:** pre-public, `Underwriting-Markdown-Private-1.0` on GitHub
**Surfaces under review:** spec/, packages/uwmd-core, packages/uwmd-cli, packages/uwmd-excel, tools/*, conformance/, governance + OSS scaffolding

---

## Executive Summary

UW Markdown is a substantially more mature project than its "v1 release blockers" framing suggests. Nearly everything the README and ROADMAP claim is shipped is actually present and wired together: a normative format spec, a protocol spec with EBNF-grade rigor, seven JSON Schemas, a multi-tier conformance corpus, a reference TypeScript library with a real safe-expression calc engine, a VS Code extension, a single-file web viewer, a calc-aware web editor, an Excel converter that shares a canonical calc pack with the library, a standalone CLI, a VitePress documentation site, CI workflows, issue templates, CODEOWNERS, a published security policy, and an RFC pipeline with six v2 drafts.

The intellectual quality is high. The framing — "the move CommonMark made for prose, OpenAPI made for APIs, JSON Schema made for data, applied to underwriting" — is precise and well-defended in the spec. Architectural decisions (append-only history with supersede, dual prose+JSON representation, _meta provenance on every block, hard pipeline-state machine, four-tier conformance ladder) are coherent and defensible. The calc engine is genuinely well-engineered: a 320-line safe-expression parser feeding a 190-line evaluator and a 17-function builtin set, with a parity test that evaluates each multifamily metric through both the in-engine evaluator and the AST-to-Excel emitter and asserts agreement to six decimals. That parity test is the kind of thing that signals the maintainer understands what "no calc drift" actually means in practice.

The remaining issues are real but tractable: documentation has spec-grade rigor at the boundary but no on-ramps for newcomers, the README has stale "(in progress)" labels on surfaces that are actually shipped, the project is still single-maintainer, security disclosure routes through a personal email, several v1 quality bars (coverage thresholds, fuzzing, mutation testing, broader fixture corpus) are unaddressed, and the agent host (Tier 4) is structurally untested because conformance can't run a live LLM in CI.

The verdict: this is **publishable on its core surface today**, would benefit from one more documentation/QA pass before the public flip, and has a clear runway to v1.1 / v2 through the RFC system.

## 1. Thoroughness

The format spec (`spec/UW_FORMAT_SPEC_v1.md`) is organized into seven Parts plus three appendices and registers 21 standard sections with a 22nd meta-section for `x_*` extensions. The protocol spec (`spec/UW_PROTOCOL_v1.md`, 747 lines) covers conformance language, the four capability tiers, display conventions, view models, edit semantics, extensibility, the module system, the calc engine contract (with EBNF grammar in §VIII.1 and a typed builtin table in §VIII.3), the AI host contract, and an explicit out-of-scope section. Together they constitute the kind of two-document structure that good standards bodies converge on (RFC + companion implementer guide, JSON Schema spec + JSON Schema metaschema), not what hobby projects typically produce.

Coverage is uneven in two places worth flagging. First, the validator implements exactly the CC-01 through CC-10 cross-section consistency checks the spec promises, but the validator also has roughly twenty additional financial-validity and meta-integrity checks that are not given identifier codes. Tools that surface validator output to users will display a mix of `CC-01`-style identifiers and free-form messages, which weakens the "every issue has a code, title, remediation, and spec_ref" promise of protocol §III.6. Either every check should get a registered code or the spec should distinguish "consistency codes" from "validity messages" explicitly.

Second, the spec registers 21 standard sections but the parser, validator, and view-model registry only deeply support a subset of them. Sections like `borrower_sponsor`, `covenants`, `due_diligence`, `compliance`, `custom_calculations`, and `custom_scenarios` exist in the registry and the example file but have no view-model entries in `BUILTIN_VIEW_MODELS` and no corresponding cross-section checks beyond CC-08 (appraised value). For Tier-1 readers this is fine — the spec says unknown sections render as default cards — but it means the "21 sections" claim is closer to "21 sections registered, ~10 with first-class tooling support."

The example file (`examples/Parkview-Apts-Glendale-AZ.uw.md`) is realistic and complete: 48-unit garden multifamily with a 52-line frontmatter, populated quick_metrics, full rent roll with unit-type breakdown and loss-to-lease, populated debt structure, sources-and-uses, NOI model, and supersede history. It is the right level of detail for a standards example. There is one further example file (`parkview-after-L6.uw.md`) showing a post-risk-rating variant; a second wholly different deal (different asset subtype or different loan type) would round out the example corpus and is cheap to produce.

The conformance corpus has eight fixtures across four tiers (2 Tier-1, 3 Tier-2, 2 Tier-3, 1 Tier-4 shape-assertion). This is enough to gate the existing implementations honestly but small enough that a determined adversary could build a "barely conformant" reader that passes Tier-1 by hard-coding section names. Adding a few intentionally-malformed fixtures (truncated frontmatter, mismatched fence annotations, supersede chains with cycles) would make the corpus a real adversarial test rather than a happy-path test.

## 2. Professionalism

The OSS scaffolding is, somewhat unusually for a solo project, complete and consistent. LICENSE is plain MIT with the canonical copyright form. CODE_OF_CONDUCT.md is Contributor Covenant 2.1 verbatim. SECURITY.md sets a 5-business-day acknowledgment window and a 90-day fix target with explicit in-scope and out-of-scope categories — including the protocol-relevant `safe-expression MUST NOT eval` and "private bank deployments are out of scope" carve-outs that experienced security reviewers care about. CONTRIBUTING.md is structured around the editorial-vs-normative split that GOVERNANCE.md formalizes, and the RFC template (`docs/rfcs/0000-template.md`) actually has the eight sections an RFC needs (summary, motivation, proposed change, compatibility, conformance impact, reference impl, alternatives, unresolved questions, prior art) rather than the empty skeleton most projects ship. Issue templates exist for bug, feature, and spec-question, with the spec-question template explicitly distinguishing format-spec, protocol-spec, and schema changes. CODEOWNERS routes spec, schema, and reference-library paths to the BDFL with a comment explaining how to allocate ownership when maintainers join.

The CI surface is real. `.github/workflows/ci.yml` runs three jobs: lint (Biome), build-and-test on a Node 20/22 matrix that also runs the conformance suite for Tiers 1–3, and a separate validate-schemas job that compiles every JSON Schema with ajv 2020 + ajv-formats. `.github/workflows/release.yml` is keyed on `v*` tags, runs the full gate (test + conformance + schema validation), and publishes both `@uwmd/core` and `uwmd` to npm with provenance. The release workflow's preamble even documents the one-time setup steps (npm org registration, token creation) the BDFL still needs to do. This is more rigorous than most v1.0 OSS releases.

The CHANGELOG.md is the single most professional artifact in the repo. It commits to "the format is based on Keep a Changelog and the project follows semantic versioning per surface (the format, the protocol, and each package each carry an independent semver)" — which is the right answer for a project with one spec stream and several implementation streams — and the `[Unreleased]` section then narrates every shipped surface in implementer-grade detail. The Tier-3 calc engine entry, for example, explains both the new EBNF productions for `&&`/`||` and the unsigned convention for `pmt`/`pv`/`fv`/`nper` so an implementer reading just the changelog could reproduce the behavior. Most projects don't write changelogs this way; this one does.

The places professionalism slips are mostly cosmetic. The README still labels the protocol spec and the conformance corpus "(in progress)" even though both are listed as ✅ Shipped in ROADMAP.md and have been substantively complete for several commits. The repo URL hard-coded in package.json files still says `Underwriting-Markdown-Private-1.0` — the rename to `uw-markdown` is in the pre-public-flip checklist but appears in many files that will need to be updated atomically. The Quick Start tells users to run `npx uwmd init my-deal.uw.md` and then qualifies "once `uwmd` is published to npm" — that's the right caveat, but it weakens the read for first-time visitors who need to recognize they're looking at a not-yet-public project. The security email is `jaredmaxey@icloud.com`, a personal address; even before the project flips public this should be a project-controlled address (e.g., a `security@` alias on a domain the project actually owns) so reporting survives any change in maintainer.

A handful of small details I'd flag: the package version surfaces are `format 1.1`, `protocol 1.1.0`, and `@uwmd/core 1.0.0`. The semver-per-surface argument in the changelog is correct, but a single `VERSIONS.md` table (or a section in `GOVERNANCE.md`) reconciling the three streams would help adopters who are trying to pin to a "v1 stack."

## 3. Design and Architecture Logic

The high-level design is strong because it answers the right "why" questions before any "how" questions.

**Why a markdown-based format and not JSON or YAML.** The spec answers this directly under "Design Principles" — `.uw.md` is dual-readable: an analyst can open the file in any markdown editor and see prose, tables, and JSON; a tool can ignore the prose and consume the JSON. That dual-readability is the entire reason the format will spread or fail to spread, and the spec recognizes it as the central design constraint rather than an aesthetic preference. The comparison set is correct: CommonMark (prose), OpenAPI (APIs), JSON Schema (data) — formats that succeeded specifically because they nailed the human/machine duality.

**Why append-only with supersede, instead of CRDTs or git-style merges.** The supersede model means every block carries a `_meta.superseded` boolean and a `_meta.supersedes` reference, and the compactor can produce a "live view" while preserving full history inline. This is the right decision for a regulated domain — credit memos need an audit trail, and "the file is the audit trail" is a much weaker integration story than "the file IS the audit trail." A CRDT or git-style approach would have been over-engineering; the append-only model gives 80% of the benefit at 5% of the complexity.

**Why a four-tier conformance ladder.** Tier 1 (Reader), Tier 2 (Editor), Tier 3 (Calc Host), Tier 4 (Agent Host) lets implementers self-certify against just the surface they care about. Web viewers don't need to parse calc grammar; an Excel converter doesn't need to host an LLM. This is structurally how OpenAPI tooling and JSON Schema tooling segmented over time, and copying that pattern early is correct.

**Why a separate protocol spec from the format spec.** The format spec defines the file; the protocol spec defines what conforming software has to do with the file. Keeping these split is right because the format will outlive any individual implementation contract — a v2 protocol could ship without changing the file format. This is exactly the lesson HTML's evolution (DOM separated from markup) and JSON Schema's evolution (validator semantics separated from schema dialect) teach.

**The calc engine is the most architecturally interesting choice.** A 320-line recursive-descent parser produces an AST; a 190-line evaluator walks it; a 17-function builtin set covers the financial primitives (`pmt`, `npv`, `irr`, `fv`, `pv`, `nper`) and the math primitives (`abs`, `floor`, `ceil`, `sqrt`, `pow`, `log`, `exp`). The engine is sandboxed: it can't read globals, can't allocate unbounded memory (input capped at 4096 chars), and can't perform side effects. The same AST then drives `emitExcelFormula()`, which translates the safe expression to Excel syntax through a caller-supplied named-range map. The parity test in `packs/packs.test.ts` evaluates each MULTIFAMILY_PACK metric through both paths and asserts the outputs agree to six decimals. That parity test is what closes the "calcs in the spec MUST match calcs in Excel" loophole that kills most data-format-and-Excel-export projects, and the fact that the maintainer thought to write it before shipping is one of the strongest design signals in the repo.

**Sandboxing of the writer/editor surface is also done right.** `applyEdit()` is a dispatcher over four operation types (`frontmatter_set`, `section_replace`, `section_supersede`, `pipeline_log_append`), each gated by `BUILTIN_EDIT_POLICIES`. A web app, a CLI, and an LLM agent all go through the same dispatcher, so there is exactly one place where "what edits are valid" is enforced. This mirrors the design pattern Anthropic itself uses for tool use — one tool definition, many surfaces — and is the right call here.

**The `@uwmd/core/browser` subpath export is a quietly important design choice.** It excludes `@anthropic-ai/sdk` and the agent runner so the same parser/validator/editor/calc engine can be bundled into a web app without dragging in a Node-only LLM client. The web editor uses it; the docs site can use it; any third-party browser tool can use it. This is the "isomorphic library" pattern done correctly.

The places I'd push back architecturally are smaller. The frontmatter parser is hand-rolled inline scalar parsing rather than `js-yaml` in safe-load mode. This was probably a deliberate dependency-minimization choice (only one runtime dependency, `@anthropic-ai/sdk`, is currently shipped), but it means YAML 1.2 features that adopters might reasonably use — anchors and aliases, multi-line literal scalars (`|` / `>`), explicit type tags, complex nested structures — will silently fail or produce surprising results. Either the parser should be hardened with explicit "we accept this subset" documentation in the spec, or the spec should formally forbid the unsupported YAML features and the validator should reject files that use them. Right now a deal file that happens to use a multi-line `|` scalar in `notes` could pass the validator but produce a broken parsed structure.

The renderer's PDF and DOCX output paths are stubs that explicitly defer to "an external rendering pipeline (Puppeteer, docx package)." This is the right call for v1 — pinning a PDF engine into the reference library would balloon the dependency surface — but the protocol spec should either say "PDF/DOCX rendering is out of scope for the reference library" or define the contract a third-party renderer must satisfy (CSS variables for badges, structured data for embeddings, etc.). Right now the surface is half-defined.

The agent-host architecture (`runBancroftAgent`, `WRITE_UW_SECTION_TOOL`) is tightly coupled to Claude through `@anthropic-ai/sdk`. The protocol §IX defines an "AI Host Contract" abstractly, but the reference implementation is Claude-specific. There is no port of the same contract to OpenAI, Gemini, local models, or a no-LLM-rules-engine agent. For v1 this is defensible — one reference is better than zero — but the architecture promise is that the contract is provider-neutral, and the implementation doesn't yet demonstrate that. A second backend (even a stub one) would prove the abstraction.

## 4. Documentation Assessment and Gaps

What's there is excellent. The format and protocol specs together are roughly the size of the JSON Schema 2020-12 spec and are written with the same conformance language (`MUST`, `SHOULD`, `MAY`). The schemas in `spec/schemas/` use 2020-12 with a `$id` pointing at the canonical `https://uwmd.org/schemas/` namespace. The CHANGELOG is implementer-grade. The RFCs (six drafts) all use the template properly and have substantive prose under each section heading rather than placeholder text. The VitePress docs site assembles spec + protocol + schemas + conformance + governance into a single browsable surface and uses a prebuild step to keep repo-root markdown as the single source of truth. CONTRIBUTING.md, GOVERNANCE.md, MAINTAINERS.md, and SECURITY.md are all present and substantive.

What's missing is the on-ramp. There is no tutorial, no "your first .uw.md in 5 minutes," no glossary, and no troubleshooting page. The Parkview example is excellent reference material but it is not a teaching artifact — a reader who has never seen the format gets dropped into a 300-line file with full rent roll, supersede history, and pipeline state, all at once. A two-page "guided tour" that walks through the simplest possible deal file (frontmatter + deal_context + one rent_roll block + nothing else), explaining each piece, would dramatically reduce the activation cost. The docs site is the natural home for this.

A glossary is a noticeable absence given the domain. Terms like "supersede," "pipeline state," "loss-to-lease," "debt yield," "DSCR," "coverage ratio," "T-12," "stabilized," and "cash-on-cash" are used throughout the spec without ever being defined in one place. Adopters from outside CRE need this. Adopters inside CRE need it for the format-specific terms (supersede, pipeline state, _meta provenance) that are not industry-standard. A `docs/GLOSSARY.md` keyed by term, with cross-references to where each term is normatively defined in the specs, is straightforward to write and would be widely linked.

Several documentation surfaces would meaningfully shorten the path from "found this on GitHub" to "filing a PR":

- **A migration / authoring cookbook.** "How do I represent a JV with three sponsors?", "How do I supersede just the rent roll without touching the operating statement?", "How do I add a custom_calculations block?", "How do I write an extension section?". These are the questions the example file implicitly answers; making them explicit accelerates adoption.

- **A troubleshooting / FAQ.** Common validator errors with explanations, common parser-rejected inputs, calc-engine grammar pitfalls (precedence between `&&` and `||`, null-propagation surprises). The validator already has remediations under `BUILTIN_REMEDIATIONS`; surfacing them in a single FAQ page makes them discoverable.

- **A conformance authoring guide.** Right now `conformance/README.md` describes the structure but not the process — how to add a fixture, what makes a good fixture, what fields are stripped before comparison, how to handle volatile data. The conformance gate is the project's central trust anchor for third parties; documenting how to extend it is high-leverage.

- **A "tools comparison" page on the docs site.** Web viewer (Tier-1, drag-drop), VS Code extension (authoring), web editor (Tier-2/3, calc-aware editing), CLI (any tier, programmatic), Excel converter (export to xlsx). New users need a decision tree for which tool to reach for.

- **An ARCHITECTURE.md at the repo root.** The CONTRIBUTING guide describes how to contribute; an ARCHITECTURE doc describes how the codebase is organized so contributors don't have to reverse-engineer it from commit history. Sections: format-spec → protocol-spec → reference-library → conformance corpus → tools, with arrows showing what depends on what.

- **A VERSIONS.md or compatibility matrix.** Three semver streams (format 1.1, protocol 1.1.0, library 1.0.0) is the right design but it is hard for adopters to reason about. A small table — "library 1.0.x supports format 1.1 and protocol 1.1.x; format 1.2 will require library 1.1.x" — removes that ambiguity.

- **A "calling convention" guide for the calc engine.** The protocol §VIII.1 has the EBNF, but adopters writing calcs need worked examples: how to reference a section field, how to coalesce nulls, how to structure conditionals, how the unsigned convention for `pmt`/`pv`/`fv` interacts with sign conventions in legacy underwriting models.

The README itself needs a quick maintenance pass: drop the stale "(in progress)" labels on the protocol spec and the conformance corpus (both are shipped per ROADMAP.md), and either remove the `npx uwmd init` quickstart until the package is actually published or add a clearer "this project is pre-public; the npm install path will work after the v1 tag" callout.

Documentation that exists but isn't linked anywhere: the `tools/web-viewer/README.md`, the `tools/vscode-uwmd/README.md`, and the per-tier conformance READMEs. The docs site appears to surface the conformance ones; the tool READMEs should be linked from a single tools index page.

## 5. Governance Assessment and Gaps

The governance model is well-specified for a single-maintainer project that intends to grow. The BDFL-with-RFC-process model is the right pattern at this size — a multi-maintainer model is overhead with no benefit when there's one person — and GOVERNANCE.md explicitly defines the trigger for promotion (5+ merged PRs + 3 constructive reviews + spec familiarity) and the trigger for the model to shift from BDFL-final to majority-of-maintainers-with-BDFL-veto (3rd maintainer added). The 14-day RFC comment window is in line with established standards bodies. Editorial-vs-normative is a meaningful distinction and is enforced via CODEOWNERS routing spec/schema changes through the BDFL.

The gaps are real and mostly stem from this still being a one-person project that hasn't yet seen its first external contributor.

**Bus-factor risk.** The BDFL model is fine; the BDFL being the only person who can release, accept normative changes, and respond to security issues is the actual problem. I'd suggest formalizing a "succession plan" section in GOVERNANCE.md: who has access to the npm tokens, who has admin on the GitHub repo, what happens to the security email if the BDFL is unavailable for >30 days, and how a successor BDFL is selected. Standards bodies that survive their founders all have this; ones that don't, don't.

**Security email is personal.** `jaredmaxey@icloud.com` is fine for receiving issues today but it is a future migration cost the moment the project has a domain (`uwmd.org` based on the schema URLs). Stand up `security@uwmd.org` (or whatever the canonical domain becomes) and put it in SECURITY.md before going public. The same applies to the contact in CODE_OF_CONDUCT.md.

**No public RFC tracking.** The six v2 RFCs are drafts in the repo, but there is no GitHub Discussion thread, issue, or other public surface where comments are collected during the 14-day window GOVERNANCE.md prescribes. The process is documented; the venue isn't. Either pin "Use the PR comments" in CONTRIBUTING.md and make sure every RFC has a tracking PR, or stand up GitHub Discussions and put one thread per RFC there.

**No release cadence policy.** GOVERNANCE.md describes how decisions get made but not how often releases happen. A short "we cut releases when X" rule (every accepted RFC gets a release, or quarterly, or on-demand-with-a-week-notice) would help adopters predict version churn.

**No deprecation policy.** When a protocol field is renamed or removed, what's the contract with adopters? RFC 0001 (locale negotiation) and RFC 0003 (custom asset-class declarations) will both eventually deprecate v1 surfaces. A short "deprecation policy" section — at least one minor version of `WARN`-level validator output, then removal at the next major — would let implementers plan.

**No conflict-of-interest disclosure.** The README names underwriter.cc as the first public consumer; the BDFL is presumably affiliated with that product. A short disclosure in MAINTAINERS.md ("the BDFL is the founder of underwriter.cc; the format and the product develop in parallel; the spec MUST NOT contain underwriter.cc-specific affordances") would head off the inevitable "is this an open standard or a vendor format?" question that every standards body faces.

**Trademark and naming.** Is "UW Markdown" or "uwmd" intended to be a trademark? If yes, it needs a usage policy for downstream tools claiming conformance ("Tool Foo is a Tier-2 conformant uwmd editor" — is that an allowed claim?). If no, it should be explicitly disclaimed. CommonMark's experience with this is instructive.

**Self-certification governance.** The conformance docs say implementers self-certify, but there's no process for adding a third-party tool to a "conforming implementations" list, no procedure for revoking a claim, and no process for handling "Tool X claims Tier 3 but its calcs are wrong" disputes. This is fine pre-public; it has to exist before downstream tools can credibly cite the standard.

**Minor pieces.** The PULL_REQUEST_TEMPLATE could include a "spec impact" checkbox that triggers the editorial/normative split explicitly. ISSUE_TEMPLATE should add a "security report" stub that points users at SECURITY.md (currently security reports go through the email channel without a github surface — fine, but newcomers will try to file an issue first). An NOTICE.md file is unnecessary under MIT but a CONTRIBUTORS.md / AUTHORS.md (auto-generated from git) is conventional and makes future contributors visible.

## 6. Further Development Priorities

Treating "should ship before public flip" and "should ship before v1.1" and "v2 territory" as separate buckets:

### Pre-public-flip (small, high-leverage)

- **README pass.** Drop stale "(in progress)" labels; reconcile quickstart with not-yet-published npm packages; add a one-paragraph "current status" banner ("UW Markdown v1 is feature-complete; the public flip is gated on org rename and the first npm publish").
- **Docs site cleanup.** Add the missing on-ramps (tutorial, glossary, troubleshooting) before the docs site becomes the public face of the project.
- **Security email migration.** `security@<domain>` instead of `jaredmaxey@icloud.com`.
- **VERSIONS.md.** Compatibility matrix between format, protocol, library, CLI, web-editor, Excel converter.
- **One additional Tier-1 fixture and one additional Tier-3 fixture.** Including a deliberately-malformed file and a calc that exercises null propagation through `&&`/`||`.
- **Coverage tracking.** Vitest coverage reporter wired into CI with a soft threshold (start at the current measured number, ratchet up).

### v1.1 (next minor)

- **Validator parity with spec.** Either give every validator check a registered code in `BUILTIN_REMEDIATIONS` or formally distinguish "consistency codes" from "validity messages" in the protocol spec. Right now the implementation surface is mixed.
- **YAML parser hardening.** Either move to `js-yaml` (safe-load) or document the supported subset and reject the unsupported subset explicitly.
- **Second example deal.** A different asset subtype (e.g., suburban office, neighborhood retail, hospitality once RFC 0006 lands) so the example corpus shows the format isn't multifamily-only.
- **Round-trip Excel.** `.xlsx` → `.uw.md` is currently deferred. Until it ships, the Excel converter is a one-way export, and the "single source of truth" claim is asymmetric. Even a 70%-fidelity reverse path (multifamily inputs only) would close a major adoption objection.
- **Section-coverage roadmap.** Document which of the 21 registered sections have first-class view-models, which have validator coverage, which have edit policies, and which are "registered but BYOI" (bring your own implementation). Make the asymmetry visible.
- **Property-based / fuzz tests on the parser and calc engine.** `fast-check` over the calc grammar would catch parser/evaluator drift cheaply. The parser's regex-bounded inputs are a natural fuzzing target.
- **Provider-neutral agent host port.** A second backend for the AI host contract (even a deterministic mock, or an OpenAI-API-shape adapter) would prove the contract is provider-neutral.

### v2 territory (already drafted as RFCs)

The six RFCs already cover the right v2 surface: locale negotiation, module signing, custom asset-class declarations, language-agnostic conformance runner, stochastic calculations, hospitality module. Two pieces I'd add to the v2 backlog that aren't currently RFCs:

- **A normative test runner specification.** RFC 0004 starts the language-agnostic runner conversation; the missing piece is an RFC that turns the runner output (TAP14 + JSON manifest is the right answer) into a published "conformance certificate" format that adopter tools can include in their releases. CommonMark's `cmark` test harness is the precedent.
- **A formal "deal lifecycle" spec.** The Bancroft layers (L0–L7) are referenced in the format spec and the example file but only sketched. A separate document — "The .uw.md Deal Lifecycle" — covering ingestion, screening, underwriting, structuring, compliance, risk, assembly, and the agent contracts at each stage would let agent-host implementers (Tier 4) target a defined contract instead of inferring it from the example file. RFC 0003 (custom asset-class declarations) and RFC 0006 (hospitality module) both implicitly assume this lifecycle exists; making it explicit is overdue.

### Domain-correctness improvements (independent of v2)

The financial logic is solid where it's implemented but shallow in places:

- **Sensitivity tables are framework-only.** The spec mentions stress_tests but the calc engine evaluates one expression at a time; there is no built-in for "compute DSCR across a 3×3 grid of rent-growth and exit-cap scenarios." A `sensitivity_table()` builtin or a multi-expression evaluator would unlock the most-used real-world stress workflow.
- **Lease-up modeling.** Rent roll is a snapshot; nothing in the format models the trajectory from current to stabilized rents. For value-add deals this is the entire underwriting story. A `lease_up_schedule` section or a stochastic-calc variant (RFC 0005 is in scope) would close this.
- **DSCR amortization sensitivity.** The current `dscr = noi / annual_debt_service` formula doesn't handle the IO-to-amortizing transition that drives the Parkview example's `dscr_warning_amortizing` flag. A canonical `dscr_amortizing()` builtin (or a guidance note that says "the DSCR builtin is point-in-time; for IO-burnoff scenarios use a stress test") would prevent every adopter from re-implementing this.
- **Currency handling.** The format is implicitly USD. RFC 0001 (locale negotiation) covers display formatting but not currency. A "currency" frontmatter field with a v1.1 default of `USD` and a v2 expansion to multi-currency models would prevent painful retrofits later.
- **Round-trip verification for valuations.** The validator catches LTV / loan-amount / purchase-price inconsistencies (CC-02, CC-03, CC-10). It does not catch "the cap rate implied by NOI / value disagrees with the stated cap rate." Adding CC-11 ("implied cap rate from noi_model and valuation must match valuation.entry_cap within 0.1%") closes a common source of model error.

## 7. Inconsistencies, Half-Finished Surfaces, and Watch-Items

A short list of specific items I'd queue for the next housekeeping pass:

- **README "(in progress)" labels** on protocol spec and conformance — both are shipped.
- **Repo URL** still says `Underwriting-Markdown-Private-1.0` in `package.json`, the docs site index, and a few other places. The pre-public-flip checklist tracks this; flagging it here for visibility.
- **L3 layer is missing** from the pipeline_state in the Parkview example (L0, L1, L2, L4, L5, L6, L7 present). Either it was reserved and skipped intentionally — in which case the spec should say so — or it's an off-by-one that needs reconciling.
- **Three semver streams** is the right design but adopters will conflate them. VERSIONS.md fixes this.
- **`confidence` vs. `human_review_required`** in `_meta` — the spec doesn't define what "high confidence + human_review_required: true" means. Either define their independence explicitly or pick one.
- **PDF/DOCX renderer stubs** — define the third-party contract or formally remove these from the protocol §VII rendering targets.
- **Grammar drift risk.** The calc engine grammar exists in three places: protocol §VIII.1 (EBNF), `src/calc/parser.ts` (recursive descent), and `src/packs/excel-emit.ts` (translator). There's a parity test for evaluation; there isn't a parity test for grammar. A "grammar fixture" set (50 expressions, parsed AST as JSON, expected Excel output) would guard against drift across all three.
- **No discussion forum.** GitHub Discussions, a mailing list, or even a pinned issue thread per RFC. The 14-day comment window in GOVERNANCE.md needs a venue.
- **Tier-4 conformance is shape-only.** This is unavoidable in CI (LLMs aren't deterministic; cost) but a "recorded fixture" approach — capture a real Bancroft run as a JSON tape and replay it deterministically — would let Tier-4 conformance gate on something more than schema validity.
- **Single-currency assumption** in the formatter and calc engine is undocumented. Document it; mark multi-currency as v2 (under RFC 0001 or a new RFC).

## 8. Verdict

UW Markdown is a serious, well-engineered, conceptually sharp standards project. The format and protocol specs are written like specs, not READMEs. The reference library is small enough to fit in one head and rigorous enough to survive a real conformance gate. The decision to share a canonical calc pack between the library, the web editor, and the Excel converter — and to write a parity test that proves they don't drift — is the kind of judgment call that distinguishes "looks like a standard" from "behaves like a standard." The governance scaffolding is more complete than most v1.0 OSS releases. The four-tier conformance ladder, the dual prose/JSON representation, the append-only supersede model, and the safe-expression calc sandbox are all defensible architectural decisions made for the right reasons and documented in the right places.

What's still soft is mostly on the seams: documentation on-ramps, a few stale labels, the bus-factor of a single maintainer, the absence of a public RFC venue, the YAML-parser-vs-spec ambiguity, and several validation/calc surfaces that are framework-only. None of these block the public flip. All of them are tractable in a v1.0 → v1.1 cycle. The pre-public-flip checklist in ROADMAP.md is realistic; finishing it and one round of documentation polish would put the project on a credible runway.

The most important question this review can't answer: whether the format will be adopted. That's not a function of the code or the spec — it's a function of whether at least one major lender, GP shop, or analytics vendor commits to round-tripping `.uw.md` in production. The technical groundwork to support that adoption is in place.
